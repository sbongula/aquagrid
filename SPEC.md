## 1. What we are building

> **AquaGrid** — an AI that forecasts an island's water demand, schedules desalination
> against the solar forecast, and catches leaks before anyone notices.

A mobile app for the operator of a desalination plant on an isolated island. On a small
island, desal is the single largest electrical load, and the water tank is effectively a
battery you can charge when the sun is out. AquaGrid decides, hour by hour, whether to
run the pump — using a trained demand forecaster, a real solar forecast, and a lookahead
scheduler — and explains every decision in plain language.

Four things make it an AI system rather than a dashboard:

1. **Predict** — a trained RandomForest forecasts water demand 48 hours ahead.
2. **Decide** — a lookahead scheduler picks pump hours to minimise diesel.
3. **Explain** — an LLM writes the operator briefing and answers questions about it.
4. **Detect** — residual analysis against the forecast flags leaks automatically.

## 3. Architecture decision — read this before writing code

**There is no live backend, and this is deliberate.**

Python trains the model on a laptop and exports its predictions to a JSON file. The Expo
app bundles that JSON as a static asset and runs all scheduling, leak detection, and
charting in JavaScript on-device.

Why: a laptop-hosted API reached from a phone means LAN IPs, ngrok tunnels, CORS, and
cold starts — the four most common ways a hackathon demo dies at hour four. Exporting to
JSON removes every one of those failure modes.

What we gain: **the app works with zero connectivity**, which is precisely the situation
on an isolated island. Say this out loud in the demo video. It is a feature, not a
compromise.

Is the AI still real? Yes. The model is trained and evaluated in Python, the metrics are
in the README, and its predictions drive every decision the app makes. "Trained offline,
inference on-device" is how most production mobile ML actually ships.

```
┌─────────────────────┐         ┌──────────────────────────────┐
│  Python (laptop)    │         │  Expo app (phone)            │
│                     │         │                              │
│  synthetic history  │         │  forecast.json (bundled)     │
│         ↓           │         │         ↓                    │
│  RandomForest ──────┼────────▶│  scheduler.js  (decisions)   │
│         ↓           │ writes  │  leak.js       (anomalies)   │
│  Open-Meteo solar   │ JSON    │  charts        (SVG)         │
│         ↓           │         │         ↓                    │
│  forecast.json      │         │  Groq LLM (optional briefing)│
└─────────────────────┘         └──────────────────────────────┘
```

## SECTION A — ML pipeline (already built)

Two files, already written and verified. Run them once; they produce
`app/assets/forecast.json`.

```bash
cd ml
pip install -r requirements.txt      # numpy, pandas, scikit-learn
python generate_data.py              # writes water_history.csv (17,520 rows)
python train_model.py                # trains, evaluates, writes ../app/assets/forecast.json
```

**`generate_data.py`** synthesises two years of hourly demand with genuinely learnable
structure: twin daily peaks (06–08, 18–20), weekends +30%, tourist season (Jun–Aug) +22%,
demand rising ~3.5% per °C, plus Gaussian noise. The patterns are real, so the model
learns something real.

**`train_model.py`** trains a `RandomForestRegressor` on a **chronological** split — the
final 60 days are held out, so it is tested on the future, never on shuffled rows. It then
fetches a live 48-hour solar forecast from Open-Meteo (no API key) and predicts demand
forward.

**Verified metrics** (quote these in the README; re-run to confirm):

| Metric | Value |
|---|---|
| MAE | **45.3 L/h** |
| RMSE | 57.0 L/h |
| R² | **0.987** |
| Naive "predict the mean" MAE | 409.7 L/h |
| Improvement over naive | **89%** |
| Top features | hour (0.90), tourist season (0.03), weekend (0.03) |

Two details already handled that are easy to get wrong: Open-Meteo is called with
`timezone=auto` (the island is UTC+12; UTC timestamps would put peak solar at local
midnight), and the array is sized to 320 m² so peak output only clears the pump draw for
a few midday hours — an oversized array means the scheduler has no decision to make.

**If Open-Meteo is unreachable**, the script falls back to a modelled clear-sky curve and
labels it in `weather_source`. The build never blocks on the network.

## SECTION B — Logic modules (pure JavaScript, no React)

Keep these free of React imports so they can be unit-tested with plain `node`.

### B1. `src/logic/scheduler.js`

```js
export function runSchedule(hourly, plant, { lookaheadHours = 12 } = {})
```

Returns:

```js
{
  steps: [{
    time, hour, solarKw, demandL,
    action,        // 'pump' | 'off'
    source,        // 'solar' | 'hybrid' | 'diesel' | 'none'
    pumpedL,       // 0 or plant.desal_output_lph
    tankL, tankPct,
    dieselL,       // litres burned this hour
    reason         // human-readable string, shown in the UI
  }],
  totals: {
    dieselL, pumpHours, solarPumpHours, hybridPumpHours,
    dieselPumpHours, shortageHours, waterDeliveredL, co2Kg, costUsd
  }
}
```

**Derived constants:**
```js
const pumpKw   = plant.desal_pump_kw;                              // 42
const outLph   = plant.desal_output_lph;                           // 6000
const cap      = plant.tank_capacity_l;                            // 60000
const floorL   = cap * plant.reserve_floor_pct / 100;              // 15000
const targetL  = cap * plant.tank_target_pct  / 100;               // 55200
```

**Per-hour decision, evaluated in strict priority order.** The first matching rule wins.

```
tankBefore = tank level entering this hour

// Lookahead: will we breach the reserve floor within the next 12h
// if we only ever pump on full solar?
horizon        = hourly.slice(i, i + lookaheadHours)
projDemand     = sum of horizon predicted_demand_lph
projSolarHours = count of horizon where solar_kw >= pumpKw
projSupply     = projSolarHours * outLph
willBreach     = (tankBefore + projSupply - projDemand) < floorL

RULE 1 — EMERGENCY
  if tankBefore < floorL
    action = 'pump'
    source = solarKw >= pumpKw ? 'solar' : (solarKw >= 0.25*pumpKw ? 'hybrid' : 'diesel')
    reason = "Below 25% reserve floor — emergency top-up regardless of cost"

RULE 2 — FREE SOLAR
  else if solarKw >= pumpKw AND tankBefore < targetL
    action = 'pump'; source = 'solar'
    reason = "Solar output {solarKw} kW covers the full {pumpKw} kW pump draw — free water"

RULE 3 — PRE-EMPTIVE HYBRID
  else if willBreach AND solarKw >= 0.5*pumpKw AND tankBefore < targetL
    action = 'pump'; source = 'hybrid'
    reason = "Shortfall forecast within 12h — topping up on partial solar now
              to avoid a full-diesel run tonight"

RULE 4 — RELUCTANT DIESEL
  else if willBreach AND tankBefore < floorL * 1.4
    action = 'pump'; source = 'diesel'
    reason = "Shortfall forecast and no usable solar — running on diesel"

RULE 5 — HOLD
  else
    action = 'off'; source = 'none'
    reason = tankBefore >= targetL
      ? "Tank near target — holding"
      : "Solar below pump draw and reserves healthy — waiting for sun"
```

**Then settle the hour:**
```js
pumpedL   = action === 'pump' ? outLph : 0;
dieselKwh = action === 'pump' ? Math.max(0, pumpKw - solarKw) : 0;
dieselL   = dieselKwh * plant.diesel_l_per_kwh;
tankAfter = clamp(tankBefore + pumpedL - demandL, 0, cap);
if (tankAfter <= 0) totals.shortageHours += 1;
```

**Totals:** `co2Kg = dieselL * 2.68` (kg CO₂ per litre of diesel).
`costUsd = dieselL * 1.60` (island-delivered diesel; state the assumption in the README).

Rule 3 is the intelligence of the whole system — spending a little diesel now during
partial sun to avoid spending a lot tonight. Make sure it visibly fires in the demo.

### B2. `src/logic/baselines.js`

Two comparison strategies over the identical forecast, so the savings number is honest.

```js
export function fixedTimerSchedule(hourly, plant)   // pumps 01:00–05:00 daily, always
export function reactiveSchedule(hourly, plant)     // pumps whenever tank < 80%, ignores solar
```

Both return the same shape as `runSchedule`. The fixed timer is how these plants are
actually run today — a wall timer set to off-peak grid hours, which on a solar island is
exactly backwards, because 01:00–05:00 has no sun and burns 100% diesel. That contrast is
your headline number.

### B3. `src/logic/leak.js`

```js
export function simulateSensor(steps, { leakStartHour = null, leakRateLph = 450, noiseStd = 120 })
export function detectLeak(steps, sensorLevels, { window = 3, zThreshold = 3.0 })
```

`simulateSensor` produces what a real float sensor would report: the scheduler's modelled
tank level, minus cumulative leak once `leakStartHour` passes, plus Gaussian noise.

`detectLeak` is residual analysis against the forecast — this is the payoff for having a
model at all:

```
expectedDrop[i] = demandL[i] - pumpedL[i]           // what the forecast says should happen
actualDrop[i]   = sensor[i-1] - sensor[i]           // what the sensor says did happen
residual[i]     = actualDrop[i] - expectedDrop[i]   // positive = losing water we can't explain

sigma = std(residual over the first 12 hours)  // or noiseStd if that is degenerate
z[i]  = residual[i] / sigma

ALERT when z[i] > zThreshold for `window` consecutive hours.
```

Returns:
```js
{
  alert: true,
  startedAtIndex: 14,
  startedAtTime: "2026-08-30T14:00",
  estimatedRateLph: 438,          // mean residual across the flagged run
  totalLostL: 3504,
  confidence: 0.97,               // map max z onto 0–1, cap at 0.99
  message: "Tank losing 438 L/h more than forecast since 14:00. Probable leak on the north line."
}
```
When no anomaly: `{ alert: false }`.

### C3. Screen structure — `App.js`

One `SafeAreaView` + `ScrollView`. No navigation library — a single scrolling screen is
faster to build and demos better than tabs.

Compute once on mount with `useMemo`:
```js
const smart    = runSchedule(forecast.hourly, forecast.plant);
const dumb     = fixedTimerSchedule(forecast.hourly, forecast.plant);
const sensor   = simulateSensor(smart.steps, { leakStartHour: leakInjected ? 14 : null });
const leak     = detectLeak(smart.steps, sensor);
```

`leakInjected` is a `useState(false)` toggled by the demo button — flipping it recomputes
and the alert appears live.

Component order down the screen:

### C4. Charts with `react-native-svg`

Do not add a charting library. Version drift against the Expo SDK is a real risk and
these charts are ~60 lines each.

- **`SolarDemandChart`** — `<Svg width={screenWidth - 32} height={180}>`. Scale each
  series to its own y-range. Solar: `<Path>` with `fill` at 0.25 opacity. Demand:
  `<Polyline>` stroke, no fill. Threshold: `<Line strokeDasharray="4 4">`. Hour labels
  every 6 hours as `<SvgText>`.
- **`PumpTimeline`** — no SVG needed. A flex row of 24 `<View>`s with `flex: 1`,
  `height: 44`, and a background colour.
- **`TankGauge`** — no SVG needed. Nested `<View>`s: a track, an absolutely-positioned
  fill at `width: ${pct}%`, and two 2px marker lines.
- **`ModelCard`** importances — a row of `<View>`s with proportional widths.

Helper for both SVG charts:
```js
const x = (i, n, w) => (i / (n - 1)) * w;
const y = (v, min, max, h) => h - ((v - min) / (max - min || 1)) * h;
```

## SECTION D — AI briefing (`src/lib/ai.js`)

### D1. Provider: Groq free tier

You asked about avoiding paid keys — **Groq is the right answer.** It serves open-weight
models (Llama 3.3 70B, GPT-OSS), signup needs **no credit card**, the key is issued
instantly at [console.groq.com](https://console.groq.com), and the API is
OpenAI-compatible so the request body is the standard shape. Free tier is roughly 30
requests/min and ~14,400/day — vastly more than a demo needs, and it is fast enough that
the briefing appears while the judge is still looking at the screen.

Alternatives if Groq is down: **OpenRouter** free models (`:free` suffix) or **Google AI
Studio** (Gemini free tier). Both are also no-card. Do not run Ollama locally — the phone
cannot reach your laptop, which is the exact problem the architecture avoids.

```js
const GROQ_URL = 'https://api.groq.com/openai/v1/chat/completions';
const MODEL = 'llama-3.3-70b-versatile';  // verify the current name in the Groq console
```

Confirm the key works before wiring the UI:

```bash
  -H "Content-Type: application/json" \
  -d '{"model":"llama-3.3-70b-versatile","messages":[{"role":"user","content":"ping"}]}'
```

## 13. Non-goals — do not build these

Every one of these has killed a hackathon submission at hour four.

- No user accounts, login, or onboarding.
- No navigation library, no tab bar, no routing.
- No backend, database, or hosted API.
- No `eas build`, no native modules beyond `react-native-svg`, no ejecting.
- No reinforcement learning or LSTM. RandomForest is trained, evaluated, and finished.
- No real hardware or IoT integration. The sensor is simulated and the README says so.
- No dark/light theme toggle, no settings screen, no animations beyond a fade.

## 14. Known pitfalls

1. **Timezones.** Already handled with `timezone=auto` — do not "fix" it back to UTC.
2. **Oversized solar array.** If you raise the panel area, every hour becomes a solar hour
   and the scheduler has nothing to decide. 320 m² is tuned so it does.
3. **Tank too large.** 60,000 L is ~2.2 days of demand. Increase it and the reserve floor
   never binds, so Rules 1, 3 and 4 never fire and the demo looks trivial.
4. **`Promise` in `useMemo`.** The schedule computation is synchronous; only the LLM call
   is async. Do not mix them.
5. **Hardcoding the savings number.** A judge will ask how it was computed. Compute it.
